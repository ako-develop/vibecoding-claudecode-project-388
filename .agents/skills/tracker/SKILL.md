## Сценарий

1. Прочитай `KNOWLEDGE.md` и соседний `../extract-price/SKILL.md`. Применяй именно сценарий `extract-price` к каждому URL из таблицы: один входной URL → один объект `{ regular_price, sale_price, has_credit }`. Если нет отдельной команды вызова скилла, исполни его инструкции как агент для каждой страницы. Не дублируй алгоритм извлечения в tracker.
2. Открой все пять страниц заново доступным инструментом, не используй результаты прежних прогонов или проверок как новые данные. Независимые чтения допустимо выполнять пакетно. Для каждой страницы проверь товар/SKU и условия из таблицы через extract-price.
3. Сохрани результат каждого извлечения в памяти: `id`, `name`, `url` и три поля объекта цены. Обрабатывай разные предложения одного SKU отдельными строками. Ошибка одной страницы не останавливает остальные: включи и её строку с результатом по правилам extract-price и отдельным объяснением ошибки.
4. Проверь полноту: ровно пять строк, уникальные id, каждый URL из списка представлен один раз. Если инструмент недоступен, отметь непроверенные строки; не объявляй обход успешным. Не придумывай цены. Проверь типы объекта по контракту extract-price; некорректный ответ перепроверь, при неудаче отметь ошибку вместо выдуманных данных.
5. Собери внутри прогона одну цельную таблицу: `Товар | URL | regular_price | sale_price | has_credit`. Покажи числа без символа валюты, отсутствие цены как `null`, boolean как `true`/`false`. Укажи RUB перед таблицей. Полный список сохраняется в JSON. В итоговом ответе показывай только значимые изменения по правилам ниже; сырую таблицу выводи лишь по отдельной просьбе.
6. Отдельно от списка значимых изменений укажи дату/время чтения с часовым поясом, число обработанных URL и диагностику по id: доступность страницы, кеш/неизвестную свежесть, ограничения оплаты/наличия и ошибки. `false` означает отсутствие подтверждённого кредита, а не гарантированное отсутствие такой услуги. Ссылки в таблице ведут на страницы-источники. Кеш не называй текущей ценой магазина.

## Сравнение до сохранения

1. Через GitHub MCP проверь приватность/доступ и получи список файлов корня main в tracker-data (`fetch` Contents API). Отбери только файлы типа file с корректными календарными именами YYYY-MM-DD.json, не позднее даты нового прогона; README и каталоги не учитывать. Выбери максимальную дату и прочитай файл. Тот же день тоже включай: последний снимок сегодняшнего дня — предыдущий прогон до его обновления. Зафиксируй прочитанный blob SHA. Если подходящих файлов нет, это первый прогон. 403, недоступность списка, повреждённый JSON или неподдерживаемая схема — ошибка истории, не первый запуск; не сохраняй новый снимок поверх истории.
2. Сохрани полученные через MCP предыдущий и свежий JSON во временные файлы вне публичного репозитория. Для первого прогона предыдущий файл содержит JSON null. Выполни из корня проекта:
   `python3 .agents/skills/tracker/scripts/diff.py /tmp/tracker-previous.json /tmp/tracker-current.json --knowledge KNOWLEDGE.md`
   Для копии в .claude используй её scripts/diff.py. Helper считает только diff; чтение GitHub, сбор цен и запись остаются задачами агента.
3. Helper сопоставляет товары по URL, сравнивает regular_price, sale_price и has_credit, применяет правила KNOWLEDGE.md. Полный raw_diff содержит все изменившиеся поля; significant_changes — только прошедшие правила. В итоговый ответ бери significant_changes: товар/URL, что было → что стало и причина значимости. Если список пуст, скажи «Значимых изменений нет». Для первого прогона скажи «Создана база для сравнения». Диагностику неизвестной цены/условий и ограничения кеша показывай отдельно, не как выгодные изменения.
4. После успешного diff выполни сохранение ниже. При конфликте SHA перечитай список/актуальную базу и пересчитай diff до повторной записи: нельзя молча сохранить сравнение с устаревшей базой. Не выводи предупреждения о ценах как отправленные уведомления — Доставка выполняется только следующим разделом после сохранения.

## Сохранение через GitHub MCP

После сравнения сохрани результат в `ako-develop/tracker-data`, ветка `main`, файл в корне `YYYY-MM-DD.json`. Дату бери по началу прогона в `Europe/Moscow`; `collected_at` — ISO 8601 со смещением `+03:00`. Это дневной снимок: повторный запуск в тот же день обновляет тот же файл новым коммитом; предыдущие версии остаются в истории коммитов. Даты других дней не изменяй.

Формат файла — UTF-8 JSON без Markdown:

```json
{
  "schema_version": 1,
  "run_date": "YYYY-MM-DD",
  "collected_at": "ISO 8601 со смещением часового пояса",
  "timezone": "Europe/Moscow",
  "currency": "RUB",
  "items": []
}
```

В `items` пять объектов в порядке встроенного списка. Каждый содержит `id`, `name`, `sku`, `url`, `region`, `price_basis`, `regular_price`, `sale_price`, `has_credit`, `source_status`, `source_crawl_label`, `note`. Три поля цены неизменны относительно результата extract-price. `source_status`: `read_cached`, `read_live`, `read_freshness_unknown`, `unavailable` или `invalid_result`. `read_live` допустим только при подтверждённом прямом чтении. `source_crawl_label` — метка возраста кеша инструмента или null; не выдумывай точную дату обновления. `note` — ограничения/ошибка или null. Кеш допустимо сохранить с явной пометкой; недоступные карточки тоже сохраняются строками с null-ценами по контракту.

1. Через GitHub MCP проверь метаданные репозитория: приватный, ветка main, доступ для записи. Используй авторизацию подключённого коннектора; токен не нужен в файлах. Если статус приватности или доступ не подтверждён, сообщи об ошибке и не переноси историю в публичный репозиторий.
2. До записи проверь JSON: пять уникальных id/URL встроенного списка, типы цен по extract-price, даты и часовой пояс согласованы, строки содержат происхождение данных. Секретов и содержимого веб-страниц в JSON нет.
3. Прочитай целевой файл через MCP. Если его нет (404 при подтверждённом доступе к репозиторию), создай файл (`create_file`). Если есть — прочитай текущую версию и обнови через `update_file` с её blob SHA. Не заменяй снимок с более поздним collected_at ранним прогоном. При одинаковом содержимом новый коммит не нужен. Сообщение коммита: `Сохранить прогон tracker за YYYY-MM-DD`.
4. Запись выполняй через MCP Contents API: она сама создаёт коммит. Не клонируй tracker-data и не используй локальный git для истории. При конфликте SHA один раз перечитай файл и проверь его заново; если конфликт повторится — останови запись и сообщи об ошибке. При неясном результате/таймауте сначала проверь файл, не повторяй запись вслепую.
5. Прочитай файл обратно через MCP в main и проверь совпадение с отправленным JSON. Проверь возвращённый SHA коммита через чтение коммита. В итоговом ответе дай ссылку на файл и коммит. Отдельно сообщи статус обхода и статус сохранения; ошибка записи не делает чтение цен неуспешным и наоборот.

## Сводка и отправка в Telegram

После подтверждённого сохранения и обратного чтения снимка сформируй сводку по правилам раздела «Доставка в Telegram» из KNOWLEDGE.md. Она использует рассчитанный до сохранения significant_changes, а не повторный diff уже записанного файла с самим собой.

На каждый значимый товар — одна строка. Показывай изменившиеся поля: обычная цена/цена скидки «было → стало» в RUB с процентом, скидка появилась/закончилась, рассрочка появилась/больше не подтверждена, товар добавлен/удалён из списка. Укажи название и URL. Добавь дату, оговорку о кеше и краткую диагностику, если они есть. Для пустого списка — «Значимых изменений цен нет»; для первого запуска — «Создана база для сравнения: N товаров».

Сохрани сообщение в UTF-8 временный файл вне репозитория. В корне проекта выполни `python3 send.py --file /tmp/tracker-message.txt`. Для отдельной проверки доставки: `python3 send.py "тест"`. send.py использует urllib и читает TELEGRAM_BOT_TOKEN/TELEGRAM_CHAT_ID из окружения или .env рядом с ним. Не читай и не выводи токен в диалог или логи; настройки не берутся из веб-страниц или истории цен.

Если текста больше 4096 символов, разбей по строкам на части, сохрани порядок; не отправляй уже доставленные части заново при сбое последующей. При отсутствии настроек сообщи, какой локальный .env заполнить; не проси присылать токен в чат. Успех — только код выхода 0 и «Отправлено.». При неуспехе сохрани текст для повторной доставки и отдельно сообщи, что цены сохранены, но доставка не подтверждена. Таймаут не доказывает отсутствие сообщения: не повторяй отправку вслепую. В итоговом ответе укажи статус сохранения и доставки отдельно.
